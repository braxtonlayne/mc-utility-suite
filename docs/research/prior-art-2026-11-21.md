# Prior art for combat, parkour assist and route following (2026-11-21)

This research pass was done under a hard time limit, about 8 minutes. It follows up on
`baritone-for-parts-2026-11-21.md`. Licenses marked **(verified)** were confirmed by a search during this pass. Licenses
marked **(known)** come from well-established project history and should be checked against the repo's LICENSE before
any copying. **(unverified)** means not confirmed.

Reuse verdicts for this All-Rights-Reserved mod:
- **copy OK:** MIT, Apache or BSD. Keep the copyright notice in a `THIRD_PARTY_NOTICES` file.
- **learn only / reimplement:** GPL, LGPL, AGPL or unlicensed. Don't paste the code. LGPL is allowed only as a separate,
  unmodified library, the way Baritone is used now.
- **data/algorithm only:** a paper, talk or formula. Reimplement it from the description.

## Best 5 to study first

1. **prismarine-physics** (MIT): a tick-exact port of vanilla player movement. Use it as an oracle to check
   `MovementPhysics` and as the reference for the hit-trade solver's forward simulation.
2. **mineflayer-pathfinder** (MIT): its movement generator, parkour moves and costs, plus the "simulate the jump before
   committing" idea. Short enough to port directly.
3. **mineflayer-pvp** (MIT, verified), plus its successor `@nxg-org/mineflayer-custom-pvp` (license conflicting, see
   below). These cover cooldown-aware attack timing, strafing, crit and w-tap patterns. Strafing and timing ideas carry
   over directly.
4. **MPK Mod 2 / FPK Mod / mcpk.wiki:** the parkour community's exact formulas for jump distance, momentum, 45-degree
   strafing and timing. This is the data the parkour intent assist needs to judge whether a jump is possible and which
   inputs make it.
5. **Celeste's Player.cs plus game-feel talks on assist design** (data/algorithm): coyote time, jump buffering, corner
   correction and how to tune "forgiveness" without it showing. This is the blueprint for a parkour assist that follows
   the player's intent.

## 4. Aim / movement assist design and human-like input

| Source | What | What to take | Verdict |
|---|---|---|---|
| [Celeste source (NoelFB/Celeste)](https://github.com/NoelFB/Celeste) | `Player.cs` released for reference | Coyote time, jump buffer, corner correction, variable jump. The repo is source-available, not open-source (unverified exact terms). | learn only |
| Maddy Thorson, "Celeste & Forgiveness" (Medium/Twitter thread) | Write-up | List of invisible forgiveness mechanics | data/algorithm only |
| Halo/Destiny aim assist (Bungie GDC talks; Jaime Griesemer "The Illusion of Intelligence"/aim-assist interviews) | Talks | Magnetism vs friction (slow-down near target) vs bullet bending. For us that means slowing the camera near the jump edge or target, never snapping. | data/algorithm only |
| [WindMouse (Ben Land)](https://ben.land/post/2021/04/25/windmouse-human-mouse-movement/) | Human-like mouse path algorithm (gravity + wind) | Feed our rotation curve with WindMouse-style jitter, capped by the 450 deg/s limit | algorithm only (original code was in GPL SMART, so reimplement) |
| Fitts's law (MacKenzie 1992, "Fitts' law as a research and design tool") | HCI model | Turn time is a + b*log2(D/W + 1), so humanized turns should take longer to reach a small, distant target | data/algorithm only |
| Apex/Titanfall movement talks (Respawn GDC) | Talks | Momentum preservation and input-buffered tech that feels skillful but forgiving | data/algorithm only |
